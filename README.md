# INuvem — painel privado da loja Nuvemshop

Painel web (Next.js + Neon + Vercel) para administrar os produtos da loja na Nuvemshop.
A Nuvemshop é a fonte da verdade; o Postgres (Neon) é um espelho para busca rápida e histórico.

**Status:** Fase 1 (base) concluída — login, conexão OAuth, cliente HTTP com rate limit, migrations e sync completo/incremental.
Próximas: catálogo (2), variantes e imagens (3), operações em massa (4), categorias/dashboard/histórico (5) e webhooks.

## Arquitetura (resumo)

- `app/` — páginas (App Router), rotas `/api/*` e Server Actions.
- `lib/nuvemshop/` — SDK tipado (uma função por endpoint) + `client.ts` (único ponto de saída HTTP: fila/rate limit por loja,
  retry com backoff em 429/5xx, timeout, logs estruturados, token nunca logado).
- `lib/sync/` — motor de sincronização retomável (cursor em `sync_runs`, lotes curtos por causa do timeout da Vercel).
- `lib/catalog/` — catálogo (Fase 2): consulta com filtros sobre o espelho (`query.ts`), regras de edição (`edit.ts`) e o
  salvamento (`update.ts`): confere conflito com a loja, envia só os campos alterados, atualiza o espelho e grava em `audit_log`.
- `lib/catalog/variants.ts`, `update-variant.ts`, `images.ts` — edição de variantes (SKU, preço, promocional, estoque) e de imagens
  (enviar arquivo, remover, reordenar, tornar principal): validação, detecção de alteração por fora, espelho e `audit_log`.
- `lib/bulk/` — operações em massa (Fase 4): `operations.ts` calcula a pré-visualização (antes → depois, o que fica de fora e por quê),
  `repo.ts` guarda o lote e os itens (`bulk_jobs`, `bulk_job_items`), `engine.ts` aplica em passos curtos e retomáveis e reverte.
  Fluxo: escolher produtos na lista → configurar a operação → **pré-visualizar (nada vai à loja)** → confirmar → aplicar (cada produto é
  conferido na loja antes de alterar; se mudou, fica de fora como "conflito") → opcionalmente **reverter o lote**.
- `lib/categories/` — categorias (Fase 5): árvore, criar/renomear/mover/apagar com regras (sem ciclos, sem nome repetido no mesmo nível,
  não apaga categoria com subcategorias), detecção de alteração por fora e `audit_log`.
- `lib/dashboard/` e `lib/history/` — indicadores do painel inicial (cada "ponto de atenção" abre a lista de produtos já filtrada) e o
  histórico pesquisável das alterações (`audit_log` com o nome do que mudou).
- `lib/webhooks/` — webhooks de produtos e categorias (`/api/webhooks/nuvemshop`, público, autenticado por HMAC): busca o estado
  atual na API e atualiza o espelho; registro idempotente dos eventos (`register.ts`), acionado pelo botão "Registrar webhooks" no painel.
- `lib/auth/` — Neon Auth (magic link) + allowlist de admins (`admins`). Exige e-mail verificado.
- `lib/crypto.ts` — AES-256-GCM para o token da loja (`ENCRYPTION_KEY`).
- `db/migrations/` — SQL puro, aplicado por `npm run db:migrate`.

Segurança: o token da Nuvemshop fica só no servidor, criptografado. O browser nunca fala com a Nuvemshop nem com o banco.
A autorização é feita no servidor (sessão + allowlist) em toda página e rota de API. RLS está ligado em todas as tabelas, sem
políticas (nega qualquer acesso por roles que não sejam a dona, como a Data API).

## Setup local

```bash
npm install            # usa .npmrc (legacy-peer-deps)
cp .env.example .env.local
```

1. **Neon:** `neon deploy` já grava `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `NEON_AUTH_BASE_URL` em `.env.local`.
   Para a Vercel use a connection string **pooled** (`DATABASE_URL`).
2. Gere os segredos que faltam:
   ```bash
   openssl rand -base64 32   # NEON_AUTH_COOKIE_SECRET
   openssl rand -base64 32   # ENCRYPTION_KEY (precisa ter exatamente 32 bytes)
   openssl rand -hex 32      # CRON_SECRET
   ```
3. Preencha `NUVEMSHOP_*` (próxima seção) e `ADMIN_EMAILS` (seu e-mail).
4. Banco: `npm run db:migrate` e `npm run db:seed-admin` (libera os e-mails de `ADMIN_EMAILS`).
5. **Neon Auth — magic link:** Console do Neon → projeto → branch `production` → **Auth → Plugins → Magic Link → ligar**
   (expiração sugerida: 15 min). Em **Auth → Configuration**:
   - adicione o domínio de produção (URL da Vercel) em *Trusted domains* (localhost já é permitido);
   - **desative o cadastro por e-mail/senha** (*Email & Password → Allow sign up*) e o login Google se não for usar.
     O painel já exige e-mail verificado + allowlist, mas desligar reduz a superfície.
   - e-mail: o remetente compartilhado serve para desenvolvimento; para produção configure um provedor próprio.
6. `npm run dev` → http://localhost:3000.

## App no Portal de Parceiros da Nuvemshop

1. Crie uma conta em https://partners.nuvemshop.com.br e um **app** (tipo privado / para sua própria loja).
2. **URL de redirecionamento (callback):** `https://SEU-APP.vercel.app/api/nuvemshop/callback`
   (para testes locais use um túnel HTTPS; a Nuvemshop exige HTTPS).
3. **Permissões (scopes):** `read_products` e `write_products`.
4. Copie o *App ID* (`NUVEMSHOP_APP_ID`), *Client ID* e *Client Secret* para as variáveis de ambiente.
5. **URLs de webhooks de LGPD** (Portal de Parceiros → seu app):
   - `store/redact` → `https://SEU-APP.vercel.app/api/nuvemshop/webhooks/store-redact` (apaga os dados da loja; exige assinatura HMAC válida)
   - `customers/redact` → `https://SEU-APP.vercel.app/api/nuvemshop/webhooks/customers-redact`
   - `customers/data_request` → `https://SEU-APP.vercel.app/api/nuvemshop/webhooks/customers-data-request`
   Os clientes da loja ficam espelhados nos Contatos (item 54): `customers/redact` (assinatura válida e `orders_to_redact`) apaga o cliente e o contato ligado; `customers/data_request` só registra. Os logs não levam dados pessoais.
6. Instale o app na loja e, no painel INuvem, clique em **Conectar loja Nuvemshop**.
7. **Nunca** cole o Client Secret em chats/commits. Se vazar, regenere no Portal e atualize a variável na Vercel.

## Deploy na Vercel (plano Hobby)

1. Importe o repositório; framework Next.js (padrão).
2. Cadastre **todas** as variáveis de `.env.example` em *Settings → Environment Variables* (inclua `APP_URL` com a URL final).
3. **Cron:** `vercel.json` agenda `GET /api/cron/sync` uma vez por dia (07:00 UTC) — o máximo do plano Hobby.
   A Vercel envia `Authorization: Bearer $CRON_SECRET`; a rota rejeita qualquer outra chamada.
   Entre os crons, o botão **Sincronizar agora** faz o incremental sob demanda (e os webhooks, quando entrarem, mantêm o espelho em tempo real).
4. As rotas de sync usam `maxDuration = 60` e processam em lotes (`SYNC_TIME_BUDGET_MS`, padrão 20 s), retomando de onde pararam.

## Verificar a configuração

- **Variáveis (local ou baixadas da Vercel):** `npm run check:env` valida `.env.local`; para a Vercel use
  `vercel env pull .env.vercel` e depois `npm run check:env -- .env.vercel`. Mostra só nomes e problemas (ausente, inválida,
  valor de exemplo, chave de criptografia que não tem 32 bytes), nunca valores.
- **Deploy no ar:** `GET /api/health` com `Authorization: Bearer <CRON_SECRET>` confere variáveis, conexão com o banco,
  migrations aplicadas, admins liberados e acesso ao Neon Auth. Responde 200 quando tudo está ok.
  ```bash
  curl -H "Authorization: Bearer $CRON_SECRET" https://SEU-APP.vercel.app/api/health
  ```
  (URLs de prévia podem exigir o login da Vercel antes; use o domínio de produção.)

## Segurança (revisão da Fase 5)

Modelo: painel privado de uma loja só. O navegador nunca fala com a Nuvemshop nem com o banco; tudo passa pelo servidor.

**Autorização em camadas**
1. `proxy.ts` exige sessão em tudo, exceto rotas com autenticação própria (webhooks com HMAC, cron/health com `CRON_SECRET`, login, OAuth).
   Cada exceção vale só para o caminho exato (`/login` sim, `/login-qualquer-coisa` não).
2. **Cada página, Server Action e rota de API chama `requireAdmin()`/`requireAdminApi()`** (sessão + e-mail verificado + lista `admins`).
   Não dependemos do layout: o Next pode renderizar uma página sem rodar o layout.
3. Segredos do app e da loja só no servidor (`server-only`); o token da Nuvemshop fica criptografado (AES-256-GCM) e nunca é logado.

**Entradas**
- SQL sempre parametrizado (os trechos dinâmicos são fragmentos fixos do código; limites são números internos).
- Descrição HTML sanitizada no servidor quando editada; upload de imagem confere o conteúdo real (bytes iniciais), não o tipo declarado.
- Webhooks: HMAC-SHA256 do corpo bruto com comparação em tempo constante; `store-redact` (destrutivo) também exige assinatura.
- OAuth: `state` em cookie `HttpOnly`; o callback exige sessão de admin e **não aceita trocar a loja já conectada**.

**Abuso e navegador**
- Rotas POST chamadas pela tela recusam requisições de outro site (`Origin`/`Sec-Fetch-Site`), além do cookie de sessão `SameSite=Lax`.
- Pedido de link de acesso limitado por IP (5 por 15 min) e no total (30 por hora), para ninguém encher a caixa do administrador nem esgotar a cota de envio de e-mail.
- Cabeçalhos: `X-Frame-Options: DENY` e `frame-ancestors 'none'` (clickjacking), `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS.
  Não há `script-src` de propósito (o Next injeta scripts em linha); fechar isso exigiria nonces.

**Sua parte (não dá para fazer pelo código)**
- Rotacionar `CRON_SECRET` e o Client Secret da Nuvemshop se algum dia foram colados em chat, e-mail ou tela compartilhada.
- No Neon Console → Auth: manter o cadastro de novos usuários desligado e, se não usa login com Google, **remover o provedor Google**
  (com ele ativo, qualquer conta Google poderia criar um usuário no Neon Auth; o painel ainda recusaria por não estar em `admins`, mas é uma porta a menos).
- Manter a lista `admins` só com quem deve ter acesso (`npm run db:seed-admin -- email`).
- `ENCRYPTION_KEY`: guardar uma cópia segura; trocá-la exige reconectar a loja (o formato `v1.` já permite versionar a chave no futuro).

## Pontos da documentação que ainda NÃO consegui confirmar

Marcados no código como "a confirmar". Validar com a documentação oficial / uma chamada real antes de depender deles:

1. **Versão da API na URL.** Usei `/v1/{store_id}` como pedido; a Nuvemshop também publica versões datadas. Configurável em `NUVEMSHOP_API_VERSION`.
2. **Semântica de `x-rate-limit-reset`.** Tratado como milissegundos de espera; é limitado a 30 s.
3. **Listagem vazia / página além da última** pode responder 404; tratado como lista vazia.
4. **URL de autorização OAuth** (`https://www.nuvemshop.com.br/apps/{APP_ID}/authorize`) e se o parâmetro `state` é devolvido no callback.
   Se não for, o callback depende só da sessão de admin (já exigida).
5. **Payload de `PATCH /products/stock-price`** (campos `stock` x `inventory_levels`, limite por chamada) — Fase 4.
6. **Imagens (Fase 3).** `POST /products/{id}/images` (envio por arquivo; o painel não envia imagem por URL), `DELETE .../images/{id}` e, para reordenar,
   `PUT .../images/{id}` com `position` (assumo que `position` é a posição de destino). Depois de cada operação o painel rebusca o produto,
   então a tela sempre mostra a ordem real da loja, mesmo se a regra de reposicionamento for diferente.
   **Upload de arquivo:** `POST .../images` com `attachment` (base64) e `filename`. O arquivo passa pelo servidor do painel (limite de 4,5 MB
   por requisição na Vercel): fotos maiores que 3,5 MB são reduzidas no navegador (JPEG, até 2400 px) antes do envio; o limite final é 4 MB.
   **Foto da variação:** campo `image_id` da variante (id de uma imagem do produto), enviado no `PUT` da variante.
   **Variantes (Fase 3):** `PUT /products/{id}/variants/{id}` com `sku`, `price`, `promotional_price`, `stock_management` e `stock`
   (`stock: null` = ilimitado; loja sem multi-estoque, então não uso `inventory_levels`).
7. **Assinatura HMAC dos webhooks**: assumi o header `x-linkedstore-hmac-sha256` (HMAC-SHA256 do corpo bruto com o client secret; aceita hex ou base64).
   Também a forma exata do payload de LGPD (usei apenas `store_id`) e se esses webhooks vêm assinados. `store-redact` falha fechado (401) sem assinatura válida.
8. **Endpoint de dados da loja** (nome/URL) — não consumido ainda; `stores.name` e `stores.url` ficam vazios.
9. **Edição de produto (Fase 2).** `PUT /products/{id}` com corpo parcial (só os campos alterados), `categories` como lista de IDs,
   campos multi-idioma como `{ "pt": "..." }`, e o comportamento de `updated_at`: na loja real ele **não avança** com edições, então a detecção de alteração por fora compara o conteúdo editável (não a data).
   `images[].alt` chega como objeto multi-idioma na loja real (a documentação mostra lista); o schema aceita as duas formas.
10. **Descrição (editor visual).** O HTML enviado é limpo no servidor (`sanitize-html`): só formatação de texto, links https/mailto/tel, imagens https e tabelas;
   estilos só de cor e alinhamento. Uma descrição que ninguém editou segue idêntica à da loja (não é reescrita nem limpa). Não confirmei
   quais tags a Nuvemshop aceita/remove na vitrine; se algum elemento sumir depois de salvar, ajustar a lista em `lib/catalog/description.ts`.
11. **Operações em massa.** Aplico cada alteração com os mesmos `PUT /products/{id}` e `PUT /products/{id}/variants/{id}` já usados na edição
   individual (1 leitura + 1 escrita por produto/variante), e não o `PATCH /products/stock-price` (formato não confirmado). Custo: ~2 chamadas por
   variante, no limite de 2 req/s por loja; um lote de ~190 produtos leva alguns minutos, em passos de até 30 s.
12. **Categorias (Fase 5).** `POST /categories` com `name` e `parent`, `PUT /categories/{id}` com `name`/`parent` e `DELETE`. Para mover uma
   categoria para a raiz envio `parent: null` (a API pode esperar outro valor, por exemplo `0`); se a loja recusar, a mensagem aparece na
   tela e o histórico guarda a resposta. Também não confirmei o que a Nuvemshop faz com os produtos de uma categoria apagada (o painel
   tira a categoria deles no espelho e os webhooks confirmam).
13. **Webhooks de produtos e categorias.** Nomes dos eventos (`product/created|updated|deleted`, `category/created|updated|deleted`),
   corpo `{ store_id, event, id }`, `POST /webhooks` com `{ event, url }` e o header de assinatura (item 7). Como o corpo não traz hora nem
   id de entrega, a deduplicação só descarta repetições em até 3 s; o processamento é idempotente (busca o estado atual e regrava).
   Se todas as entregas forem recusadas com 401, o nome do header de assinatura está errado (o log `webhook.rejected` mostra se ele veio).
14. **Magic link no servidor** (`auth.signIn.magicLink`) existe nos tipos do SDK `@neondatabase/auth@0.5.0-beta`
   (versão beta), mas o envio real do e-mail não foi testado fora do seu ambiente.
15. **Gerenciar variações (não testado na loja real).** O painel edita os valores de cada variante (`PUT /products/{id}/variants/{id}`
   com `values`, uma lista de `{ pt }` com um item por propriedade, na ordem de `attributes`) e o peso (`weight`, em kg; esvaziar envia
   `null`), cria variantes (`POST /products/{id}/variants`) e exclui (`DELETE`), e renomeia as propriedades (`PUT /products/{id}` com
   `attributes`). A confirmar: se `values` pode ser trocado por `PUT` numa variante existente, se `weight: null` é aceito, se a loja recusa
   excluir a última variante (o painel já impede), e se renomear uma propriedade pelo produto mantém os valores das variantes. Depois de
   cada operação o painel rebusca o produto e regrava o espelho, então a tela sempre mostra o estado real. **Fora de escopo por enquanto:**
   adicionar ou remover uma propriedade (ex.: passar a ter Cor e Tam), pois isso exige reescrever os valores de todas as variantes de uma vez.
16. **Lote "Padronizar propriedades (COR e TAMANHO)" (não testado na loja real).** Usa o mesmo `PUT /products/{id}` com `attributes`
   do item 15, em lote: renomeia as duas propriedades para COR e TAMANHO (reconhece "Cor", "COR", "Tam", "Tamanho", "CORES", "TAMAMHO"
   etc., ignorando caixa, acento e vírgula sobrando). Cada produto é conferido contra a loja antes de aplicar e o lote pode ser revertido
   (volta aos nomes anteriores). Ficam de fora, com o motivo na pré-visualização: produtos já no padrão, com a ordem invertida (TAMANHO
   antes de COR, pois os valores das variantes seguem a ordem das propriedades), com uma só propriedade, sem propriedades, com três ou
   mais, ou com nomes não reconhecidos. Na auditoria de 04/10/2026: 111 de 188 produtos seriam renomeados e 77 ficariam de fora.
17. **Lote "Padronizar grafia dos valores" (não testado na loja real).** Reescreve os valores das variantes com `PUT /products/{id}/variants/{id}`
   e `values` (mesmo ponto do item 15: se a loja aceita trocar `values` numa variante existente). Regras fixas, por nome da propriedade
   (COR/Cor/CORES e TAM/Tamanho, em qualquer ordem): **cores** com inicial maiúscula em cada palavra, mantendo "de, da, do, e, com, em" em
   minúsculas ("Verde de Água", "Preto com Branco"); **tamanhos** em maiúsculas, com "UNICO/Único/único" virando "ÚNICO". Tamanhos não usam
   inicial maiúscula para não virar "Pp"/"Gg". Outras propriedades não mudam. O produto inteiro fica de fora se duas variantes ficariam com a
   mesma combinação de valores. Cada produto é conferido contra a loja e o lote pode ser revertido. Na auditoria de 04/10/2026: 409
   variantes em 130 produtos mudariam, e nenhum produto teria variantes repetidas.
18. **Lote "Corrigir a ordem das propriedades" (não testado na loja real).** Para produtos com TAMANHO antes de COR: coloca COR e depois
   TAMANHO (`PUT /products/{id}` com `attributes`) e troca os dois valores de cada variante (`PUT .../variants/{id}` com `values`), levando
   junto os outros idiomas. Como são várias chamadas por produto, este lote é **tudo ou nada**: se uma etapa falhar, ou se, depois de
   aplicar, o painel reler o produto e a loja não estiver como esperado, ele desfaz o que já aplicou com os objetos originais da loja e
   mostra o resultado. Se nem o desfazer for aceito, o item mostra "ATENÇÃO" com o que ficou para conferir na loja. Na auditoria de
   04/10/2026: 14 produtos e 43 variantes, e em todos o primeiro valor de cada variante é um tamanho e o segundo uma cor. Ponto a confirmar:
   se a loja aceita reordenar `attributes` e trocar `values` em sequência (ver itens 15 a 17).
19. **Lote "Completar COR e TAMANHO" (não testado na loja real).** Para produtos com só uma das propriedades, ou nenhuma: acrescenta COR
   e/ou TAMANHO (sempre nessa ordem) e coloca o valor que **o usuário digita na tela** em todas as variantes do produto (a loja não tem como
   saber a cor ou o tamanho). O que o produto já tinha é mantido, com os outros idiomas. Usa `PUT /products/{id}` com `attributes` e
   `PUT .../variants/{id}` com `values`, no mesmo esquema tudo ou nada do item 18 (confere depois de aplicar e desfaz se algo falhar). A
   reversão volta ao estado anterior, inclusive a "sem propriedades" (`attributes: []` e `values: []`). Pontos a confirmar: se a loja aceita
   acrescentar uma propriedade com a lista de valores das variantes ainda com o tamanho antigo entre uma chamada e outra (se recusar na
   primeira chamada, nada muda e o item mostra o motivo), e se `attributes: []` é aceito ao desfazer. Produtos sem nome na loja (o painel
   mostra "Produto <id>") ficam fora da lista da tela. Na auditoria de 04/10/2026: 10 produtos (3 sem propriedades, 6 só com tamanho,
   1 só com cor), 11 variantes.
20. **Cadastrar produtos (não testado na loja real).** Tela "Novo produto" (botão na lista de Produtos): nome, descrição (editor, limpa como na
   edição), tags, categorias, SEO e "Publicar na loja agora" (desmarcado = rascunho). Dois modos: **produto simples** (uma variante com preço,
   promocional, SKU, peso e estoque) ou **cores e tamanhos** (o usuário digita as cores e os tamanhos; o painel monta uma variante por
   combinação, com as propriedades COR e TAMANHO, grafia padronizada, e preço/estoque padrão ajustáveis por variante; até 60 variantes). Envia
   `POST /products` com `attributes` e `variants` (cada uma com `values`) numa chamada só. Pontos a confirmar: se a loja aceita `attributes`
   e `variants` aninhados na criação, e se gera o `handle` sozinha a partir do nome. As **fotos** não vão na criação: depois de criar, o painel
   abre a tela do produto, onde o painel de imagens já existe. Depois de criar, o espelho é gravado com a resposta da loja, e o histórico
   registra "Produto criado" (também quando a loja recusa).

21. **Salvar tudo junto e excluir produto (não verificado na loja real).** O botão “Salvar na Nuvemshop” salva dados do produto, nomes das propriedades e todas as variantes alteradas (cada uma com a própria checagem de conflito; falhas aparecem por item e o que deu certo fica salvo). Criar e excluir variante continuam imediatos. “Excluir produto” usa `DELETE /products/{id}` (irreversível, exige digitar o nome); um 404 da loja só limpa o espelho. Confirme em um produto de teste que a exclusão remove variantes e imagens.
22. **Excluir produtos em lote (não verificado na loja real).** Operação "Excluir produtos" no lote: pré-visualização com a lista inteira, confirmação digitando EXCLUIR, `DELETE /products/{id}` por produto (com conferência do nome; renomeado = conflito, 404 = já excluído), espelho e histórico atualizados. Não pode ser revertido. Teste primeiro com 1 produto.
23. **SKU automático e lote "Ajustar SKUs" (não verificado na loja real).** Produto novo e variante nova com SKU em branco recebem o próximo número (maior SKU numérico do espelho + 1; digitados são respeitados). O lote "Ajustar SKUs" numera variantes sem código e renumera repetidos (a variante mais antiga fica com o código); códigos únicos não mudam; pode ser revertido. A numeração usa o espelho: sincronize antes de lotes grandes e não crie produtos em paralelo. Confirme que `PUT /products/{id}/variants/{id}` aceita `sku` (e que a loja não rejeita SKU repetido).

A lista fica em **Produtos → Rascunhos** (`/produtos/rascunhos`): *Continuar* reabre o cadastro com tudo como estava (as etiquetas “✨ Sugerido pela IA” e os destaques voltam) e *Descartar* apaga o rascunho e as fotos do Blob. Ao criar o produto, o rascunho vira “criado” e as fotos guardadas são enviadas à loja pelo servidor (padronizadas) e saem do Blob conforme sobem. Não são guardados: SKU digitado à mão e ajustes de preço/estoque por variante (o rascunho guarda os valores padrão). Exige o Blob configurado.
52. **Cadastro em lote (fase 4b, `/produtos/lote-ia`).** Link “Cadastro em lote” em Produtos e em Rascunhos. Suba até 30 fotos de várias peças misturadas; **Agrupar com a IA** (`POST /api/produtos/ia/agrupar`, miniaturas de 512 px, 20 por hora) separa por peça — ângulos, detalhes e o mesmo modelo em cores diferentes ficam juntos; fotos que a IA esquecer viram “sem grupo” e grupos com mais de 6 fotos são divididos. Também há “Uma peça por foto”, e o seletor de cada foto move entre peças, cria peça nova ou tira do lote. Cada peça tem nome provisório e um campo de anotações (tecido, tamanhos, preço). **Preparar N rascunhos** processa uma peça de cada vez: cria o rascunho, guarda as fotos no Blob, roda a mesma análise da IA do cadastro (com o tom da loja), coloca a foto principal sugerida primeiro e salva o formulário já preenchido (`rascunhoParaForm`, com as etiquetas “✨ Sugerido pela IA”). Se a análise falhar, o rascunho fica criado com as fotos e dá para refazer a análise ao abri-lo. Nada vai para a loja: você revisa cada rascunho em **Rascunhos → Continuar** e cria o produto. Sem mudança de banco.
53. **Enquadrar as fotos já no cadastro (Novo produto e rascunhos).** Cada foto do “Comece pela foto” ganhou o botão **Enquadrar**: abre o mesmo painel da tela do produto (tipo peça 1:1 / modelo 4:5; enquadramento automático, ajustar, cortar ou **manual** com mover e zoom, usando o `CropEditor`) com a prévia do resultado e a miniatura da vitrine; a miniatura da foto passa a mostrar a versão enquadrada. Ao criar o produto, cada foto sobe com o enquadramento escolhido (`aplicarEnquadramento` preenche `tipo`, `enquadramento` e `recorte` do envio). O enquadramento também é guardado no rascunho, junto de cada foto (`FotoSalva.enquadramento`; automático não ocupa espaço), e é usado quando o servidor envia as fotos do rascunho à loja. Para fotos que vieram do rascunho, a prévia usa a cópia reduzida (900 px) só para visualizar; o envio usa o arquivo guardado. Sem mudança de banco.
54. **Clientes da loja nos Contatos (`/contatos`).** Botão **Trazer clientes da loja** (e **Atualizar** / **Reler todos**) lê `/customers` da Nuvemshop (escopo `read_customers`, só leitura) em passos retomáveis (`POST /api/clientes/sync`, ~25 s por chamada; a tela repete até concluir) e espelha em `customers` (migração `0012`: nome, e-mail, telefone, documento, CEP/cidade/UF, total gasto, último pedido, aceita novidades, datas). Cada cliente vira (ou liga a) um **contato** tipo Cliente: liga a contato existente pelo mesmo CPF/CNPJ ou e-mail, **preenche só campos vazios** (nunca sobrescreve o digitado) e não recria o contato que você apagou (`ignored`). A sincronização seguinte é incremental (`updated_at_min`, margem de 10 min); há também um cron diário (`/api/cron/clientes`, 07:20 UTC) que só roda depois da primeira sincronização manual. Filtros novos: **Origem** (loja/cadastrado aqui), **Segmento** (já compraram, cadastradas sem compra, melhores 20%, novas em 30 dias, aceitam novidades) e **Ordenar por maior gasto**; selo “Loja” e total gasto na lista. No contato da loja, o card **Dados da loja** mostra total gasto, cliente desde e aceita novidades, e **Ver pedidos na loja** busca os últimos pedidos na Nuvemshop (busca por e-mail, conferindo o ID do cliente; nada é guardado). A exportação Excel ganhou Origem, Total gasto, Aceita novidades e Cliente da loja desde. Histórico: “Clientes da loja sincronizados” (só números). Os nomes de campos recebidos da API aparecem após a sincronização para conferência.
55. **Promoções agendadas (`/promocoes`, fase 1).** Em Produtos, marque produtos (ou filtre) e use **Agendar promoção**: nome, desconto em % sobre o preço, arredondamento (,90 / real inteiro), início e fim (horário de Brasília). O desconto vira o **preço promocional** das variações (migração `0013`, tabela `promotions`). Quem aplica e desfaz é o motor de lotes já existente: no início o painel recalcula o plano com os preços de então, cria um lote “Promoção … — início” (a execução confere cada produto na loja antes de gravar) e, no fim, cria o lote de **reversão**, que devolve o preço promocional de antes (o anterior, não apenas vazio) e **pula o que foi alterado na loja** durante a promoção, em vez de sobrescrever. Estados: Agendada → Aplicando → No ar → Encerrando → Encerrada (ou Cancelada, só antes de começar). Botões **Iniciar agora** / **Encerrar agora** (a tela repete o passo até terminar e retoma se fechar). Um produto não pode estar em duas promoções que se sobrepõem. Cron: o plano Hobby da Vercel só permite 2 crons, então o diário de clientes (`/api/cron/clientes`, 07:20 UTC ≈ 04:20 de Brasília) também confere a agenda (começa as que chegaram na hora, encerra as vencidas, continua as pela metade; promoção vencida sem ter começado é encerrada sem tocar na loja). Ou seja, sem “Iniciar/Encerrar agora” a precisão é de um dia. Histórico: Promoção agendada / iniciada / no ar / encerrada / cancelada. Só desconto percentual nesta fase; “liquidar parados” (fase 2) e cupons (fase 3) vêm depois.
56. **Liquidar os parados (`/promocoes/liquidar`, fase 2).** (a) **Ler as vendas da loja** (`POST /api/vendas/sync`, só leitura): lê os pedidos pagos dos últimos 365 dias (`/orders`, `created_at_min`, `payment_status=paid`; cancelados e não pagos não contam) em passos retomáveis e guarda só o resumo por produto em `product_sales` (unidades, pedidos, data da última venda; migração `0014`). Repetir uma página não conta duas vezes (marcador da página na mesma instrução SQL) e uma nova leitura substitui a anterior. (b) A lista mostra produtos **com estoque controlado > 0 e sem venda há N dias** (padrão 90; filtros de estoque mínimo e “só publicados”), do maior **dinheiro parado** (estoque × preço) para o menor; ficam de fora os cadastrados há menos de N dias (não tiveram tempo de vender), estoque ilimitado e os que já estão em outra promoção que não terminou. (c) **Sugerir descontos com a IA**: o desconto de partida vem de uma regra (15% a 40% conforme o tempo parado, +5 se há muito estoque, +5 se já tinha preço promocional; limite 10–60%) e o Claude ajusta no máximo ±10 pontos e escreve o motivo citando só os números (dias, estoque, vendas); fora disso, ou sem chave, vale a regra. Não conhece custo/margem, e o texto avisa isso. (d) Você marca os produtos, ajusta o % de cada um e **agenda como uma promoção** (mesmo ciclo da fase 1: iniciar, no ar, encerrar com restauração do preço anterior). Para isso `promotions.percents` guarda o desconto por produto e o plano é calculado por grupo de percentual. Histórico: “Vendas da loja lidas”. Desde o item 59 a leitura de vendas vem do espelho de pedidos (`product_sales` é refeito a partir dele). Ainda não verificado contra a API real: nomes dos campos de `/orders` (a tela mostra os campos recebidos).
57. **Cupons em lote (`/cupons`, fase 3).** Menu **Cupons**. Os cupons não são espelhados no banco: a lista (até 1.000, busca por código e filtro de situação: ativo, agendado, desativado, vencido, esgotado) e a exportação leem `/coupons` da Nuvemshop na hora. **Criar em lote**: prefixo (2–12 letras/números), quantidade (até 200), tipo (% ou R$), valor, validade opcional, usos por código (padrão 1; vazio = sem limite), pedido mínimo, “só primeira compra” e “soma com outros descontos”. Passo 1, **Gerar os códigos** (`POST /api/cupons/preparar`): valida e sorteia `PREFIXO` + 6 caracteres de um alfabeto sem ambiguidade (sem I, O, 0, 1), sem repetir entre si nem com os cupons que já existem; nada vai à loja. Passo 2, **Criar na loja** (`POST /api/cupons/criar`, 10 por chamada, a tela repete): cada cupom é um `POST /coupons`; o que a loja recusar fica numa fila para **tentar de novo** com o motivo, e sem permissão (401/403) a criação para. **Desativar** (`POST /api/cupons/desativar`, `PUT /coupons/{id}` com `valid: false`; não apaga, dá para reativar na loja). **Exportar Excel** (`/api/cupons/exportar`, com os filtros da tela ou só um prefixo, que a tela oferece após criar um lote): código, tipo, valor, situação, usos, limite, validade, mínimo, primeira compra e acumula. Histórico: “Cupons criados em lote” (lista os códigos), “Cupons desativados”, “Cupons exportados”. Não verificado contra a API real: nomes dos campos de `/coupons` (a listagem tolera campos a mais ou a menos) e se a autorização inclui a permissão de escrever cupons (se não, a loja devolve 401/403 e a tela mostra o aviso).
58. **SEO de categorias e páginas (`/seo/categorias`, `/seo/paginas`).** O mesmo fluxo do SEO de produtos (gerar, revisar, gravar), agora em abas **Produtos / Categorias / Páginas** em `/seo`. Sugestões em `seo_item_suggestion` (migração `0015`; tipo + id do item). **Categorias**: lidas do espelho; o Claude recebe o nome, a categoria pai, a descrição atual, quantos produtos há e até 15 nomes de produtos publicados como exemplo, e escreve o título (≤ 70, terminando em “| Donatelle Concept”) e a descrição (≤ 320) sem citar preço, promoção, frete nem material que não esteja nos dados; ao gravar (`PUT /categories/{id}` só com `seo_title` e `seo_description`) o painel confere antes se a categoria mudou na loja desde a última sincronização (se mudou, atualiza o espelho e pede para revisar), atualiza o espelho e registra “SEO da categoria gravado” no Histórico com o texto antigo. **Páginas**: lidas da loja na hora (`/pages`, sem espelho); o prompt manda ser fiel ao conteúdo e não inventar política, prazo ou valor; grava com `PUT /pages/{id}` e registra “SEO da página gravado”. Em cada aba: gerar para quem falta / gerar tudo de novo (6 por chamada), editar com contador, gravar um a um, **gravar nas que estão sem SEO** ou **em todas** (8 por chamada, para se a loja negar permissão). Não verificado contra a API real: se a autorização inclui ler/escrever as páginas da loja (se não, a aba mostra o aviso) e se `PUT /pages/{id}` aceita só os campos de SEO.
59. **Vendas e giro (`/vendas`).** Menu **Vendas**. **Ler os pedidos da loja** (`POST /api/pedidos/sync`, só leitura, em passos retomáveis de ~25 s) espelha `/orders` em `orders` e `order_items` (migração `0016`): número, data, total, desconto, situações, ID do cliente e, por linha, produto, variação, nome, quantidade, preço e os valores da variação. **Sem dados pessoais do comprador** (nada de nome, e-mail, telefone ou endereço) e, quando a Nuvemshop pede a remoção de um cliente (`customers/redact`), o ID dele é zerado nos pedidos e as vendas ficam. A primeira leitura traz os pedidos criados nos últimos 365 dias; as seguintes, só os alterados desde a última vez (`updated_at_min`, margem de 10 min), então um pedido cancelado ou reembolsado depois é atualizado; **Reler tudo** refaz a janela. O cron diário (`/api/cron/clientes`) também atualiza os pedidos depois da primeira leitura manual. Venda = pedido **pago e não cancelado**. O painel mostra, para 7 dias, 30 dias, 90 dias ou 12 meses (dias de Brasília): faturamento, pedidos, ticket médio e peças vendidas com a variação contra o período anterior de mesmo tamanho; faturamento por dia (barras, com tabela); **mais vendidos** por peças ou por valor (foto, peças, valor, estoque atual); vendas **por categoria** (produto em duas categorias conta nas duas), **por cor** e **por tamanho** (valores da variação da linha do pedido, ou da variação do espelho se o pedido não os trouxer, lidos pela posição da propriedade COR/TAMANHO do produto, com a grafia padronizada). **Exportar Excel** dos produtos vendidos no período. Ao terminar cada leitura, o resumo por produto da liquidação (`product_sales`, item 56) é refeito a partir do espelho; por isso a tela de liquidação passou a usar este mesmo botão de leitura. Histórico: “Pedidos da loja sincronizados”, “Vendas exportadas”. Não verificado contra a API real: nomes dos campos de `/orders` (principalmente `products[].product_id`, `variant_id`, `price` e `variant_values`); a tela mostra os campos recebidos após a leitura.
60. **Estoque inteligente (`/estoque`) e publicar de novo quando o estoque volta (`/automacoes`).** (a) **Republicar quando o estoque volta** (opção por loja, desligada por padrão; migração `0017`): a regra “sem estoque” (item 44) passa a lembrar, em `auto_unpublished`, os produtos que ela despublicou. Se a nova opção está ligada e chega um aviso do produto (webhook `product/updated`) com pelo menos uma variação disponível (com estoque ou sem controle de estoque), o painel publica o produto de novo, atualiza o espelho e registra “Produto publicado automaticamente (estoque voltou)” no Histórico. **Só volta o que a regra despublicou**: produto despublicado à mão nunca é publicado por ela; cada produto da lista “Despublicados por falta de estoque” tem **Manter despublicado** (não volta sozinho) e o botão **Publicar agora os N com estoque** (confere cada um na loja antes, respeita “manter”, não depende da opção estar ligada). Se alguém publicar o produto por fora, ele sai da lista de espera; o evento do próprio PUT não gera laço. (b) **Estoque inteligente**: menu **Estoque**, calculado com o espelho de pedidos (item 59; sem eles a tela pede para ler em Vendas) por **variação** com controle de estoque: ritmo = unidades vendidas na janela (14/30/60/90 dias) ÷ dias. **Repor primeiro: esgotadas que vendiam** (estoque zero com venda na janela, das que mais venderam), **Acabando em breve** (acaba em até 7/14/21/30 dias no ritmo atual, das que acabam antes) e a **sugestão de reposição** = ritmo × dias a cobrir (30/45/60) − estoque. **Exportar Excel** da reposição (situação, produto, variação, SKU, estoque, vendidas, ritmo, dias restantes, sugestão, publicado). Depende de a linha do pedido trazer a variação (`variant_id`); se a lista vier vazia havendo vendas, é por isso. Histórico: “Reposição de estoque exportada”.
61. **Carrinhos abandonados (`/carrinhos`).** Menu **Carrinhos**. Lê `/checkouts` da Nuvemshop **na hora** (últimos 14 dias, até 5 páginas; sem espelho): os dados da cliente (nome, e-mail, telefone) **não ficam guardados no painel**. Só entram carrinhos ainda não concluídos, com telefone ou e-mail, parados há pelo menos 30 min, 1 h (padrão), 3 h ou 1 dia; uma cliente com vários carrinhos aparece uma vez (o mais recente); do carrinho mais valioso para o menos. Cada carrinho mostra as peças, o valor e há quanto tempo está parado. **Escrever a mensagem** (`POST /api/carrinhos/mensagem`): o servidor relê o carrinho pelo ID e o Claude escreve uma mensagem curta de WhatsApp no tom da loja (primeiro nome, até duas peças, o link do carrinho, sem inventar desconto, prazo ou estoque); ao Claude vão **só o primeiro nome, os nomes das peças, o link e o cupom** (nunca telefone, e-mail nem valores). Sem a chave da Anthropic, usa um texto padrão. Opcional: **cupom de cortesia** (1% a 50%, 1 a 30 dias, 1 uso, não soma com outros descontos), criado na loja só quando você pede (com confirmação), no formato `VOLTE` + 6 caracteres; um por carrinho (se já existe, é reaproveitado) e registrado no Histórico. **Nada é enviado à cliente**: a tela devolve o texto editável e o botão **Abrir no WhatsApp** (`wa.me` com o texto) ou **Abrir no e-mail**; você decide enviar. **Marcar como contatado** (`cart_contacts`, migração `0018`) guarda só o ID do carrinho, quem e quando, e o código do cupom, para a equipe não falar duas vezes; filtros Para contatar / Já contatados / Todos. Histórico: “Carrinho abandonado marcado como contatado”, “Cupom de recuperação criado”. Não verificado contra a API real: nomes dos campos de `/checkouts` (a tela lista os campos recebidos quando não acha carrinhos) e se a autorização inclui os carrinhos (checkouts) e a escrita de cupons.
62. **Expedição (`/expedicao`).** Menu **Expedição**, sobre o espelho de pedidos (item 59; a tela traz o botão de atualizar). **Fila**: pedidos **pagos, abertos** (nem cancelados nem arquivados) e **ainda não enviados** (situação de envio diferente de enviado/entregue), do mais antigo ao mais novo, com valor, peças e foto/variação de cada item; selo **Atrasado** a partir de 1, 2 (padrão), 3 ou 5 dias corridos desde a criação do pedido, com contagem no topo e filtro “só atrasados”. **Lista de separação** (`/expedicao/separacao`, própria para imprimir): as mesmas peças de vários pedidos somadas (produto, variação, SKU, foto, quantidade e os pedidos que levam cada uma), em ordem alfabética, e uma segunda parte “Por pedido”; vale para os pedidos marcados ou para toda a fila. **Rastreio em lote**: cole linhas “número do pedido + código” (separados por `;`, vírgula, tab ou espaço, aceita `#1234`; vem direto de uma planilha) ou digite o código em cada pedido; o painel valida (5 a 40 letras e números, pedido repetido com códigos diferentes não vale), avisa o que não está na fila e marca os pedidos. **Marcar como enviados** (`POST /api/expedicao/enviar`, 10 por chamada): relê cada pedido na loja e só envia se ele ainda é uma venda paga, aberta e não enviada (se já estava enviado, só corrige o espelho), chama `POST /orders/{id}/fulfill` com o código, atualiza o espelho (migração `0019`: `orders.tracking_code`, que também é lido da loja) e registra “Pedido marcado como enviado” no Histórico com **só o número do pedido e o código** (nenhum dado da cliente). Erro num pedido não trava os outros; sem permissão (401/403) para na hora. Caixa opcional (desmarcada) para pedir à loja que **avise a cliente por e-mail** com o rastreio. A lista de separação e a fila não usam nome, endereço nem contato da cliente. Não verificado contra a API real: o endpoint de “enviar” (`/orders/{id}/fulfill`, com `shipping_tracking_number` e `notify_customer`), os valores de `shipping_status` da loja e se a autorização inclui escrever pedidos; teste primeiro com um único pedido. Pedidos para retirar na loja não são distinguidos.
63. **Correção: atualizar categoria ou página não apaga mais o resto (e restauração).** A API da Nuvemshop trata o `PUT` de categorias e páginas como **substituição**: enviar só alguns campos apaga os outros. O SEO de categorias (item 58) enviava só `seo_title` e `seo_description` e **apagou o nome, o endereço (handle), a descrição e a categoria pai** das categorias gravadas na loja. Agora `updateCategory` (`lib/nuvemshop/categories.ts`) e `updateStorePage` (`lib/nuvemshop/pages.ts`) **leem o item na loja, juntam o que mudou aos campos atuais e enviam tudo**; depois conferem o que a loja devolveu e, se algo que não era para mudar mudou, restauram o que havia e avisam (nada é gravado). Isso vale também para renomear/mover categoria em `/categorias`. **Restauração**: a tabela `category_restore` (migração `0020`) guarda os dados originais (nome, endereço, descrição, pai) e, havendo linhas pendentes, `/categorias` mostra **Restaurar categorias**, que devolve esses dados à loja mantendo o SEO atual e registra “Categoria restaurada” no Histórico.
   Ajuste: a loja responde 422 a um campo de texto enviado **vazio** (ex.: `description: {pt: ""}`), mas aceita o campo ausente (fica vazio do mesmo jeito); por isso `updateCategory`/`updateStorePage` e a restauração tiram do envio os textos sem conteúdo (`semTextosVazios`).
64. **Conteúdo padrão (`/conteudo`).** Menu Administração → **Conteúdo**. (a) **Blocos para descrições**: textos que se repetem (tabela de medidas, política de troca, cuidados) escritos uma vez no mesmo editor visual dos produtos (migração `0021`, tabela `content_blocks`; nome único por loja; o HTML passa pela mesma limpeza da descrição do produto). Há dois modelos de partida, com trechos “[preencher: …]” que precisam ser completados antes de aplicar. (b) **Aplicar em lote**: em Produtos, filtre por categoria (ou marque os produtos) → Operação em massa → “Aplicar bloco de conteúdo na descrição” (aplicar ou remover; no fim ou no começo). O bloco entra envolto em marcas invisíveis (`<!--inuvem:bloco:ID-->…`), então reaplicar **atualiza no mesmo lugar** (sem duplicar) e remover tira só o bloco. Se um editor tirar as marcas, o painel ainda acha o bloco pelo mesmo HTML. Só a descrição é enviada à loja (`PUT /products/{id}` com `description`, mantendo os outros idiomas); a pré-visualização mostra quem recebe, atualiza ou fica de fora (já tem, descrição ficaria vazia); se a descrição mudou na loja depois da pré-visualização o produto fica como conflito; o lote é reversível e registra a descrição antes/depois no Histórico. Depois de gravar, o painel confere se a loja manteve (ou tirou) a marca; se a loja limpou os comentários HTML, **desfaz e avisa** em vez de deixar o texto sem marca. Mudar um bloco não altera descrições já gravadas: reaplique o bloco. (c) **Páginas da loja com a IA** (`/conteudo/paginas`): escolha o tipo (Sobre nós, Trocas e devoluções, Entrega e prazos, Como comprar, Cuidados, Fale conosco), escreva os **fatos** e o Claude redige o rascunho usando **só esses fatos**; o que faltar vira “[preencher: …]” e aparece numa lista. Você edita no editor visual e cria a página na loja (`POST /pages`) **como rascunho (não publicada)**; só dá para publicar direto quando não resta nenhum “[preencher: …]”. Histórico: “Bloco de conteúdo criado/atualizado/excluído”, “Lote: bloco de conteúdo na descrição do produto”, “Página da loja criada”. Não verificado contra a API real: se a loja preserva comentários HTML na descrição (se não, o lote desfaz sozinho e avisa) e se a autorização inclui criar páginas (`POST /pages`).
65. **E-mails da loja reescritos com a IA (`/emails`).** Menu Administração → **E-mails**. A API da Nuvemshop (até onde se sabe, por documentação de terceiros) só tem **leitura** dos modelos de e-mail (`GET /email_templates` e `/email_templates/{id}`); **não há gravação**, então o painel **não altera os e-mails da loja**: ele reescreve o texto e você o cola no editor de e-mails da Nuvemshop. (a) **Modelos da loja**: a tela lê `/email_templates` na hora (sem espelho) e lista cada modelo com o assunto; os campos são reconhecidos de forma tolerante (assunto: `subject`; corpo: `body`/`content`/`html`…; texto simples ou multi-idioma) e, se nada for reconhecido, a tela mostra os campos recebidos. (b) **Colar um e-mail**: se a loja não entregar os modelos (ou a leitura for negada), você escolhe o tipo (pedido recebido, pagamento confirmado, enviado, carrinho abandonado, outro) e cola assunto e texto. (c) **Reescrever** (`POST /api/emails/gerar`): as variáveis da loja (`{{ … }}` e `{% … %}`) viram marcadores ⟦n⟧ antes de ir ao Claude e voltam depois, e o painel confere que **nenhuma variável sumiu nem foi inventada** e que a **sequência de tags HTML não mudou**; se a conferência falha, tenta uma segunda vez dizendo o que faltou e, se ainda assim falhar, mostra o aviso em vez de esconder. O Claude escreve no tom da marca (acolhedor, “você”, sem emojis nem promessas novas, assunto até 80 caracteres) e não inventa prazo, desconto nem política. (d) **Revisar**: assunto e HTML editáveis, prévia isolada (iframe sem scripts), original lado a lado, **Copiar assunto / Copiar texto**, “Já colei na loja” e descartar; editar recalcula o aviso de variáveis. Tabela `email_suggestion` (migração `0022`). Histórico: “E-mail da loja reescrito com a IA”, “Texto novo do e-mail colado na loja”. Não verificado contra a API real: se `/email_templates` existe para esta autorização e quais são os nomes dos campos; o modo “colar” cobre o caso contrário.
66. **Selos na vitrine (`/selos`).** Menu Administração → **Selos**. Três avisos na página de produto da loja pública: **“Últimas unidades!”**, **contagem regressiva** da promoção e botão **“Falar no WhatsApp sobre esta peça”**. (a) **Instalação, uma vez e sem API**: o painel mostra um trecho `<script async src=".../api/loja/selos.js?store=<id>">` para colar nos códigos externos da Nuvemshop (não usa a API de scripts nem exige permissão nova; para remover, apague o trecho). (b) **Como funciona**: o script (`lib/badges/script.ts`, ~70 linhas, sem cookies, sem `innerHTML`, qualquer erro é engolido) só age em `/produtos/<endereço>`, pede `GET /api/loja/selos?s=<loja>&h=<endereço>` e desenha os selos antes do botão de comprar (`.js-addtocart`, ou o formulário do produto, ou abaixo do título; se nada for achado, não mostra). (c) **Dados públicos mínimos**: `/api/loja/selos` e `/selos.js` ficam fora do filtro de login (só esses dois caminhos), respondem com CORS aberto, sem cookies, cache de 1 min (`s-maxage=60`), e só devolvem avisos de produtos **publicados**: nome, “últimas” (verdadeiro/falso, sem número), fim da promoção e o link do WhatsApp; selos desligados, loja ou produto desconhecidos, ou endereço inválido dão `{}`. (d) **Regras**: “últimas unidades” = estoque somado das variações de 1 até o limite (1–20, padrão 3) e **todas** com estoque controlado (uma variação sem controle desliga o selo); a contagem aparece nos produtos de uma promoção agendada **no ar** (menu Promoções) até o horário de encerrar; o WhatsApp abre `wa.me` com a mensagem (`{produto}` vira o nome) e o link da página, nada é enviado pelo painel. O número é normalizado para o formato brasileiro (55 + DDD). (e) **Interruptor geral** (`badge_settings`, migração `0023`, desligado por padrão): desligado, a vitrine não mostra nada mesmo com o trecho colado. A tela também tem “Ver o que a vitrine recebe” para conferir um produto. Histórico: “Selos da vitrine configurados” (antes e depois). Não verificado na loja real: onde o tema posiciona o botão de comprar (as classes `.js-addtocart`/`js-product-form` são as comuns dos temas) e se os códigos externos aceitam o trecho; teste primeiro com os selos ligados e um produto de estoque baixo.
67. **Cashback por cupom (`/cashback`) e sinais de risco dos pedidos.** O item 11 foi feito com regras conservadoras e **nada automático**: o painel propõe, uma pessoa confirma, e cada cupom pode ser cancelado. (a) **Cashback** (menu **Cashback**; migração `0024`, tabelas `cashback_settings` e `cashback_grants`, sem dados pessoais): depois de uma compra, a cliente ganha um **cupom de valor fixo, uso único, com validade e compra mínima**, criado em `POST /coupons` (nunca soma com outros descontos). Regras editáveis, com estes valores de partida: 5% do pedido (máx. 30%), teto de R$ 100 por cupom, pedido mínimo de R$ 150, compra mínima de R$ 150 para usar, validade de 30 dias, espera de 7 dias depois do pedido (tempo de troca/devolução) e **orçamento de R$ 500 por mês**. O valor é o percentual do total, para baixo em reais inteiros, até o teto. Regras fixas: só pedidos **pagos e não cancelados**, de cliente identificada, dos últimos 60 dias; uma cliente ganha **um cupom por vez** (só depois de 60 dias do anterior; cupom cancelado libera); dois pedidos da mesma cliente na lista contam como um. A emissão (`POST /api/cashback/emitir`, até 5 por chamada, a tela repete) **reavalia tudo no servidor**: elegibilidade, risco, orçamento do mês (para os seguintes quando acaba) e relê o pedido na loja para confirmar que continua pago e ativo; sem permissão (401/403) para na hora; uma disputa entre duas chamadas desfaz o cupom duplicado. O Histórico registra pedido, código, valor e validade, **sem nome nem contato**. Depois de emitido: **Mensagem para a cliente** (texto fixo, com os números reais do cupom; nome, telefone e e-mail são lidos do pedido na loja na hora e não ficam guardados; botões WhatsApp/e-mail abrem a conversa pronta, nada é enviado), **Marcar como avisada** e **Cancelar cupom** (desativa na loja com `valid: false`, não apaga, e sai do orçamento). A lista mostra a situação lida da loja (ativo, usado, vencido…) e o **custo real** (soma dos cupons já usados). (b) **Sinais de risco** (`lib/risk/signals.ts`): não é antifraude de verdade (o painel não vê pagamento, IP nem endereço; o antifraude do meio de pagamento continua valendo). São regras simples e explicáveis sobre o espelho de pedidos: primeira compra a partir de 3× o ticket mediano (só com 20+ pedidos pagos em 365 dias), 3+ pedidos da mesma cliente em 24 h, desconto de 50% ou mais do valor, 5+ unidades da mesma peça. Um sinal vira “Atenção”; **dois ou mais viram “Conferir antes de enviar”** na fila de Expedição e **retêm o pedido do cashback**. Nunca cancelam nem bloqueiam nada sozinhos. Histórico: “Regras do cashback alteradas”, “Cupom de cashback criado”, “Cupom de cashback cancelado”. Não verificado contra a API real: a permissão de escrever cupons (se negada, a tela mostra o aviso), os campos de nome/telefone do pedido (`customer.name`, `customer.phone`; sem eles a mensagem sai sem nome e sem links) e o campo `used` dos cupons. **Vale-presente** não foi feito como tela própria: um vale com saldo exige crédito da loja, que a API não oferece; para vales de valor fixo e uso único, use **Cupons → Criar em lote** (tipo valor, 1 uso).
68. **Painel do dia (início).** O cartão **Hoje** abre a página inicial (`lib/dashboard/hoje.ts`): (a) as **vendas do dia**, com pedidos pagos e faturamento de hoje, o de ontem e a média diária dos 7 dias anteriores (pedidos pagos e não cancelados, dias de Brasília, a partir do espelho de pedidos; mostra quando os pedidos foram lidos e avisa se passou de 36 horas); (b) **Precisa de ação**, do mais urgente ao menos, cada linha levando à tela que resolve: sincronização do catálogo que falhou ou está parada há mais de 2 dias, pedidos nunca lidos ou velhos, **pedidos atrasados** (2+ dias), pedidos a enviar, **pedidos para conferir** (2+ sinais de risco), variações **esgotadas que vendiam** e as que **acabam em até 7 dias** (ritmo dos últimos 30 dias), produtos despublicados que já têm estoque de volta, **promoções** que pedem ação agora, que começam ou que terminam em 24 h, **lotes** com erro ou conflito nos últimos 3 dias e em andamento, cupons de cashback sem aviso à cliente e pedidos que podem ganhar cashback. Tudo é lido **só do banco** (nenhuma chamada à Nuvemshop, então a página continua rápida), e cada parte é independente: se uma consulta falhar, ela some e o resto aparece. Os carrinhos abandonados não entram porque dependem de uma leitura ao vivo na loja (use a tela Carrinhos). O cartão “Precisa de atenção” de pendências do catálogo continua logo abaixo.
69. **Diagnóstico da API (`/diagnostico`).** Menu Administração → **Diagnóstico**. Confere, na loja de verdade, o que o painel assume sobre a Nuvemshop. (a) **Permissões do app**: compara os scopes concedidos com o que cada funcionalidade exige (gravar produtos, ler pedidos, marcar como enviado, ler clientes, ler/criar cupons, ler/criar páginas; `write_x` vale também como `read_x`) e mostra OK ou Falta. (b) **Rodar o teste** (`POST /api/diagnostico`, só leitura, até 20 vezes por hora): faz uma leitura `GET` de poucos itens (5) em cada recurso (loja, produtos, categorias, pedidos, clientes, cupons, páginas, carrinhos abandonados e modelos de e-mail), uma de cada vez, e confere campo a campo o que o painel usa, separando **obrigatórios** (sem eles a funcionalidade quebra) de **opcionais** (só perdem um detalhe) e mostrando o tipo de cada um (por exemplo se `price` vem como texto). Resultado por recurso: OK, Faltam campos (com a lista e os campos que a loja devolveu), Sem dados para conferir (a loja não tem cupons, por exemplo), **Sem permissão** (401/403), **Não existe na API** (404) ou Erro. Também confere se os **webhooks** que o painel assina estão registrados. (c) **Privacidade**: o teste e o relatório trazem **só nomes de campos e tipos, nunca valores**, então pedidos e clientes podem ser conferidos sem expor dado pessoal; o botão **Copiar relatório** gera um texto que pode ser colado numa conversa para ajustar o painel. (d) **Situações dos seus pedidos** (do banco, sem chamar a loja): quantos pedidos há em cada valor de `payment_status`, `status` e `shipping_status`, com o que o painel faz com cada um (só `paid` conta como venda; `shipped`, `delivered` e `fulfilled` contam como já enviado, o resto vai para a fila de expedição). Histórico: “Diagnóstico da API da loja executado”, só com o resumo por recurso. Nada é gravado na loja.
70. **Custos e margem (`/custos`).** Menu **Custos**. (a) **Custo por produto**, guardado só no painel (`product_costs`, migração `0025`; nada é enviado à loja): digite na tabela (salva ao sair do campo ou com Enter, vazio apaga), **importe uma planilha** .xlsx/.csv com as colunas “ID” ou “SKU” e “Custo” (formatos como `12,50` e `R$ 1.234,56`; linha com custo vazio é pulada; a resposta lista as linhas ignoradas e o motivo: custo inválido, SKU que não existe ou que aparece em mais de um produto, produto que não existe), **baixe a planilha** com ID, produto, SKU, preço e custo atual para preencher, ou **traga os custos que a loja já guarda** nas variações (média do campo `cost`, só em produtos sem custo no painel). (b) A tabela mostra o **menor preço de venda de hoje** (o promocional, se houver) e a **margem** sobre o preço ((preço − custo) ÷ preço), em verde, amarelo (abaixo da margem mínima) ou vermelho (abaixo do custo), com filtros Sem custo, Margem baixa e Abaixo do custo e busca por nome ou SKU. (c) **Margem mínima** (padrão 0%; tabela `cost_settings`): o painel **não deixa um lote baixar o preço, o preço promocional ou aplicar uma promoção abaixo de custo ÷ (1 − margem mínima)**; o produto fica de fora da pré-visualização com o motivo (“ficaria abaixo do custo (R$ 60,00)”). Só vale para produtos com custo informado e só para quedas de preço: subir o preço nunca é barrado, e a reversão de um lote não passa pela trava. (d) **Liquidação**: o desconto de partida e o sugerido pela IA nunca passam do que o custo e a margem mínima permitem (múltiplos de 5 para baixo, com a frase “Limitado a …”), e cada linha mostra o custo, o preço e a **margem depois do desconto digitado** (vermelho abaixo do custo, amarelo abaixo da margem mínima, aviso quando não há custo). (e) **Vendas**: cartão **Margem estimada** (lucro bruto, margem, custo das peças e quanto do valor vendido tem custo informado), margem por produto nos mais vendidos e duas colunas novas na planilha (custo unitário e margem média). A conta usa o **custo de hoje** nas vendas passadas, só os produtos com custo informado, e não inclui frete, taxas nem impostos. Histórico: “Custo do produto alterado”, “Custos importados de planilha”, “Custos trazidos da loja”, “Margem mínima alterada”. O Diagnóstico da API passou a conferir se as variações trazem o campo `cost`. Não verificado contra a API real: se a loja devolve `cost` nas variações (a tela funciona sem isso).
71. **Resumo diário por e-mail (`/resumo`).** Menu Administração → **Resumo diário**. Todo dia de manhã o painel manda aos administradores escolhidos as **vendas de ontem** (pedidos, faturamento e média dos 7 dias anteriores) e o que **precisa de ação** (os mesmos itens do cartão “Hoje” da página inicial: sincronização, pedidos atrasados/a enviar/a conferir, estoque, promoções, lotes, cashback), em grupos Urgente / Atenção / Para saber, cada item com link para o painel. Só números do negócio; **nenhum dado de cliente** no e-mail nem no Histórico (que guarda apenas contagens, nunca endereços de e-mail). (a) **Envio**: pela API do **Resend** (HTTP, sem biblioteca), com a variável `RESEND_API_KEY` na Vercel; sem ela a tela avisa e nada é enviado. O remetente padrão é `INuvem <onboarding@resend.dev>`, que **só entrega para o e-mail dono da conta Resend**; para outras pessoas, verifique um domínio no Resend e defina `RESEND_FROM`. (b) **Quando**: o cron diário que já lia pedidos e clientes (`/api/cron/clientes`) foi movido de 07:20 UTC para **10:00 UTC (≈ 07:00 de Brasília)** e, depois de ler os pedidos, envia o resumo; o catálogo continua sendo sincronizado às 07:00 UTC. Vale o limite do plano Hobby (2 crons). A conferência da agenda de promoções e a leitura de pedidos e clientes desse mesmo cron também passam a rodar nesse horário. (c) **Regras de envio**: desligado por padrão; no máximo **um envio automático por dia** (dia de Brasília, `last_sent_on`); opção “só enviar quando houver algo urgente ou de atenção” (nesse caso o dia não conta como enviado); falha do serviço de e-mail fica registrada na tela e no Histórico e **não** marca o dia como enviado, então a próxima execução tenta de novo. (d) **Destinatários**: até 5, **só administradores do painel** (conferido ao salvar e de novo a cada envio, então quem perde o acesso deixa de receber); isso impede que alguém use o resumo para mandar números da loja a um endereço de fora. (e) A tela mostra a **prévia** do e-mail de hoje, o último envio e o último erro, e tem **Enviar um teste agora** (assunto com “[teste]”, até 10 por hora, não conta como o envio do dia). Migração `0026` (`digest_settings`). Histórico: “Resumo diário por e-mail enviado” e “Resumo diário configurado”. Não verificado contra o serviço real: o envio pelo Resend com a chave da conta e o remetente escolhido.
